人が見ていない時間も、コーディングエージェント(Claude Code)にモデル開発を進めさせる仕組みづくり

長期間続く1 回が重い正解が無い間違いがエラーにならない

→
やったこと 改善サイクルを、ハーネスで囲む

ハーネスエンジニアリングとは

  • エージェントの基本から、ツール共通の仕組み、効く理由、設計の考え方までを順に見る

3.1エージェントの基本

  • エージェント = ツールを使い、結果を見ながら作業を進める LLM
  • 1 回で答えを返す使い方と違い、「考える → 行動する → 結果を見る」を繰り返す
ふつうの LLM の使い方
質問
→
回答
1 回で終わる
エージェント
考えるモデル
→
行動するコマンド実行・編集・検索
→
結果を見る出力・エラー
↩ 終わりの条件を満たすまで繰り返す

3.2ハーネスとは

  • エージェント = モデル + ハーネス
  • ハーネス = モデルの外側にあって、人が手を入れられる仕組みの総体
  • harness は英語で「馬具」。力の強い馬を、乗り手の思う方向に動かす道具
69.7% → 77.0%研究(AHE): モデルはそのままで、ハーネスだけを改良したときの作業の完了率
52.8% → 66.5%LangChain: モデルを固定し、ハーネスだけを変えたときの作業の完了率
  • モデルを変えなくても、ハーネスを変えるだけで結果が変わる

どちらもコーディングの課題集 Terminal-Bench 2 での結果。AHE(arXiv:2604.25850)、LangChain「Improving Deep Agents with harness engineering」(2026-02)。

3.4なぜ効くのか

  • ハーネスはモデルを賢くするのではなく、モデルの仕事を簡単にする
  • 人も同じ。買い物リストがあれば、記憶力が上がらなくても買い忘れない
モデルの仕事ハーネスなしハーネスあり
前回の結果を知る会話から思い出す(セッションが変わると消える)結果の一覧ファイルを読む
提出する手順を毎回ゼロから考える決まった手順書に沿う
学習を始める長いコマンドを毎回組み立てる用意したコマンドを 1 行打つ

考え方の出典: 認知科学の「認知的人工物」(Norman)を LLM エージェントに当てはめた解説(arXiv:2604.08224)。表の例は今回のプロジェクトから。

2023 年ごろまでプロンプトエンジニアリングどう頼むか1 回の指示文を工夫する
→

→
2026 年ごろハーネスエンジニアリングどんな環境で働かせるかエージェントが動く環境の全体を設計する

3.6設計の考え方

1書いた指示は確率的にしか守られない。守らせたいことは仕組みで

  • 記憶やツールを足すと上がり、システムプロンプトだけを変えると下がった
  • 全部入れても、単独の効果の和にはならない

AHE(arXiv:2604.25850)。bash だけを持つ最小の構成に、部品を 1 つずつ足して測った。ベンチマーク 1 つでの結果。

2部品は「モデルが単独でできないこと」への仮定。モデルが進んだら外す

  • 例: 「リファクタリングは 1 ファイルずつ」というルールは、昔のモデルの脱線を防いだが、新しいモデルには足かせになった
  • ルールファイル・手順書・hook は 3〜6 か月ごとに見直す(Anthropic の勧め)

3長時間の作業は引き継ぎをファイルで構造化する

初回機能の一覧と進捗ファイルを作る
→
毎回の始め進捗と git log を読む
→
1 機能だけ実装して確かめる
→
commit と進捗の更新
  • 会話の要約ではなく、確かめられるファイルで次のセッションに渡す

Anthropic「Effective harnesses for long-running agents」(2025-11)

4行動の前の「ガイド」と、行動の後の「センサー」を組み合わせる

行動の前ガイド
ルールファイル、手順書(skills)、地図になる資料
行動の後センサー
テスト、lint、別のエージェントによるレビュー

3.7なぜ AI モデル開発にハーネスエンジニアリングが重要か

長期間続く数か月・数百回の実験。セッションが変わるとエージェントの記憶は消える記録と地図が要る
1 回が重い学習 1 回に数時間。人は張り付けない自律で回し、止まり方を決める仕組みが要る
正解が無い良し悪しは実験しないと分からない比較と評価の仕組み、方針が要る
間違いがエラーにならない前処理のずれやデータの漏れでも、学習は正常に終わる自動チェックが要る
  • 指示文や文脈の工夫だけでは、長期の改善サイクルは回らない
  • 次の章で、そのサイクルとハーネスの対応を見る

参考: Anthropic「Effective context engineering for AI agents」(2025-09)、OpenAI「Harness engineering」(2026-02)、martinfowler.com「Harness engineering for coding agent users」(2026-04)。ハーネスを自動で探す・進化させる研究は Appendix A9。

AIモデル開発の改善サイクル

  • AIモデル開発 = 改善サイクルを長期間回し続けること
  • 自動化のゴール = このサイクルをエージェントに回させること

自動化の 2 つの課題

課題 1エージェントが自律的に作業できる環境を整える
各ステップに必要な道具と情報を用意する
課題 2長期の運用に耐える
資料が膨らみ、古い情報が残ると品質が落ちる

課題 1: ステップごとに必要な仕組み

方針を決める研究方針の文書
案を出すフォーラムの自動収集(cron・skills)、過去コンペの解法のナレッジベース
実装するskills、hook によるレビュー
学習を回す実験の待機列、/goal
評価する比べる相手との差を自動で計算するスクリプト
記録する結果ファイル、skills
分析する間違いの分析、過去の実験との比較(実験 ID と結果ファイル)
全体ルールファイル、ドキュメント管理、memory

課題 2: 長く回すほど品質が落ちる流れ

期間が延びる
→
資料が膨らむ
→
古い情報が残る新旧の方針が混在
→
エージェントが古い情報を読む
→
品質が落ちる

ハーネス = モデル以外のすべて。ルールファイル、手順書、自動チェック、定期実行など、エージェントを取り巻く仕組みの総称。

ハーネスの部品

  • 7 つの部品で改善サイクルを支えた
  • Claude Code の機能(CLAUDE.md・skills・hook・/goal)と、自作スクリプト(実験の待機列・目次の生成・cron)の組み合わせ
5.1ルールファイル毎回読む前提と、情報への地図全体 5.2ドキュメント管理資料を探せる・古さがわかる状態に全体 5.3実験管理実験を ID で指し、順に走らせ、結果を残す学習記録分析 5.4skills繰り返す作業を毎回同じ手順で実装記録 5.5hook決まったタイミングで必ず動く処理実装 5.6cron情報収集などの定期作業案出し 5.7/goal終わりの条件を満たすまで作業を続ける学習記録

5.3

実験管理(expXXX・W&B)

  • 実験を ID で指し、順に走らせ、結果を機械が読める形で残す

ベストプラクティス

1 実験 = 1 IDコード・結果・commit を同じ ID で結ぶ
1 点だけ変える比べる相手を決めてから走らせる
結果はリポジトリにエージェントがすぐ読めるファイルで残す

連番 ID(expXXX)の利点

  • 親の ID を書けば、過去の実験との比較を機械的に辿れる
  • commit・ファイル名・提出名を同じ ID で結べる

W&B との分担

W&B(Weights & Biases)= 学習曲線や指標を記録し、Web 画面で比べるサービス。MLflow の実験管理と同じ役割。

W&Bリポジトリ

5.4

skills(繰り返す作業の手順化)

  • 繰り返す作業の手順書
  • 依頼に合う skill を Claude が自動で読み込む

skill にするメリット

品質がそろう同じ依頼に毎回同じ手順で応える
指示が一言で済む「提出して」だけで全手順が実行される
不備を自動で検知手順にチェックを組み込める
文脈を圧迫しない必要なときだけ読み込まれる

ベストプラクティス

繰り返す作業だけ何度も頼む作業を対象に
依頼の言い回しを書く説明文に「提出して」などを並べる
手順だけを書く変わる値は別ファイルから読む

まとめ

AIモデル開発の自動化には、ハーネスエンジニアリングが欠かせない

  • AIモデル開発は、長く続き、1 回が重く、正解が無く、間違いがエラーにならない
  • モデルの賢さだけでは、この改善サイクルは回らない
  • サイクルを支える仕組み(ハーネス)を設計して、はじめてエージェントに任せられる

自動化できたこと、人の介入が必要だったこと

自動化できた
  • 前の実験から 1 点変えて、実験を作る
  • 学習の実行と監視、エラーからの復旧
  • 比べる相手との差の計算と、結果の記録
  • フォーラムの情報収集、コードのレビュー
  • 範囲を決めたモデル探索やプロンプトの改善
人の介入が必要だった
  • 研究の方針を決める
  • 大きな改善案を出す
  • 前提を見直す
  • 提出など、取り消せない操作の判断
  • 方針と案出しも、研究方針の 1 枚と「毎朝の 3 案」の仕組みがあれば、一部を任せられる(8 章)

明日から使える 4 つの原則

  1. 方針は 1 枚。エージェントに案を出す役を与える
  2. 変わる事実は 1 か所。変更は置き換えで残す
  3. 守らせたいルールは文章でなく仕組みで
  4. 使ってほしい道具は毎回通る手順に組み込む
いちばん伝えたいこと エージェントを賢くしようとするより、
迷わず働ける環境をつくる 指示文を磨くより、方針・事実・ルールの置き場を設計する

A9. ハーネスを自動で探す・進化させる研究

研究やり方結果
Meta-Harness
(Stanford ほか、2026)		コーディングエージェントに、過去のハーネスのコード・スコア・実行の記録を読ませ、新しいハーネスを提案させる。評価して記録し、繰り返すテキスト分類で人が作った最良を +7.7 pt。見つけたハーネスは別のモデルにも効いた
AHE
(復旦大学ほか、2026)		失敗した実行の記録から、直すべき部品を選んで書き換える。書き換えのたびに「直るタスク」と「壊れるタスク」を予測させ、次の評価で答え合わせする10 回の改良で完了率 69.7% → 77.0%。ただし「何が壊れるか」の予測はほとんど当たらなかった(適合率 11.8%)
  • どちらも、失敗の生の記録を読ませることが効いた。要約にすると、原因を探す手がかりが消える

数字はリポジトリの git 履歴・実験の待機列・結果ファイルから数えたもの。「誰が案を出したか」は記録の文言からの推定。コードの抜粋は実物から取り、長いものは一部を省いた。
