**最優先(1)**: **棚卸し表を作り、「必ず」「しない」の規則を hook と権限設定へ移す。** 移した規則は CLAUDE.md から消します。

|---|---|

PreToolUse hook の例(未適用)。`.claude/settings.json` に Bash と Edit|Write の matcher で登録する想定です。exit 2 で実行を止めると、stderr の文がエージェントに返ります。エラーの文には次に何をすべきかを書きます(Anthropic の「道具の書き方」の推奨)。

```bash
#!/usr/bin/env bash
# 例(未適用): scripts/hooks/guard_tools.sh
# 標準入力の JSON から、実行しようとしているコマンドか編集先のパスを取り出して検査する
input=$(cat)
cmd=$(printf '%s' "$input" | jq -r '.tool_input.command // ""')
path=$(printf '%s' "$input" | jq -r '.tool_input.file_path // ""')
if printf '%s' "$cmd" | grep -qE '(^|[;&| ])p(kill|grep) -f'; then
  echo "pkill -f / pgrep -f は自分のコマンドラインに当たる。止めるときは python scripts/lane.py stop <id> を使う。" >&2
  exit 2
fi
if [ -n "$path" ] && grep -qsF "$(basename "$path")" state/lanes/*.running 2>/dev/null; then
  echo "$path は走行中の runner が使っている。lane.py stop で止めてから直すか、別名のコピーを作る。" >&2
  exit 2
fi
exit 0
```

**次に(2)**: **事前登録の必須欄は lane.py 自身で検査する。** 事前登録の置き場は今は `docs/ideas.md` の候補の行(`.claude/skills/new-experiment/SKILL.md:24`)で、`results/<exp>.yaml` は学習が終わった後に作られます。なので bash の hook で yaml を見るのではなく、`lane.py add` に `--axis` `--direction` `--kb-refs` `--changes-labels` を足して `state/queue.yaml` に保存し、欠けていれば lane.py が断ります。ユーザ指示で外すときは `--reason` を付けます(`--allow-dup --reason` と同じ型)。

**自己評価と違う点:** 「特に良い対策がとれなかった」は事実と合いません。大きな整理は 5 回あります。09-07 の記録監査、09-13 の運用層の整備(CLAUDE.md を 381 行から 129 行へ、STATUS.md・skill・record.py の導入)、09-20 の Codex を使った 7 バッチの再監査(92 ファイル、10 本を archive へ)、10-08 の文書の整理(299 ファイル・参照 490 か所)、10-16 の見直しです。ideas.md は 1,204 行から 156 行へ、log.md は 3,868 行から 208 行へ縮みました。それでも、そのたびに再び膨らんでいます。実態に近いのは「**清掃が事後の一括型で、文書が膨らむ仕組みは変えなかった**」です。

**原因の見立て:**

1. **変わりやすい事実が手書きで複製されていた。** この競技の「土台」に触れている文書は、git 追跡の md から archive と他コンペの writeup(`references/competitions/`、一般語としての「土台」)を除いて約 60 ファイルあります。独立 5 表の顔ぶれは 15 ファイルに重複しています。
2. **追記型の文書が多く、上書きと経過の区別がなかった。** CLAUDE.md の行数は 145 に保たれましたが、文字数は 55% 増え、最長の行は 1,400 字です。行数の上限が、1 行を長くすることで回避されていました。「現在地は書かない」(§4)という自分の規則に反して、実験 ID が 33 種・日付が 20 個入っています。
3. **状態の行は「読むな」の警告にはなるが、新しい事実の在処にはならない。** 「…時点」「…のまま」の但し書きが INDEX に 16 か所あり、本文は古いまま状態の行だけで古さを告知していました。
4. **規則を検査する仕組みが無かった。** 「結論を ideas か experiments に 1 行で戻す」という規則に対し、`docs/studies/` の 54 本のうち 26 本(48%)は `docs/ideas.md` からも `memory/experiments.md` からも参照されていません(log.md など他の文書からは参照があります)。`docs_index.py --check` は状態の行の有無しか見ていませんでした。
5. **よく似ているが今は正しくない文書は、最も強い妨害文になる。** Chroma の context rot の研究(6 章)では、主題が近い妨害文は 1 本でも性能を下げました。古い土台・古い物差し・古い LB の数字は、まさにこれに当たります。

**実際はどうすればよかったか:**

**最優先(1)**: **変わりやすい事実を 1 か所に置く。** 例(未適用): `data/derived/baseline.yaml`。

```yaml
baseline: exp428
since: 2026-10-16          # UTC
decided_by: user
submission:                # 最良提出の構成(列ごとに rank 平均する組)
  - {exp: exp428, cols: all}
  - {exp: exp422, cols: [meniscus_med, meniscus_lat, oa_med, oa_lat]}
best_lb: {value: 0.961, date: 2026-10-15}
independent_rulers: [dread, pilkwang, lixin, claude_v1, gemma4]
decision: docs/decisions/0012-baseline-exp428.md
```

`status.py`・`label_rulers.py` の既定の `--b`・skill・提出の雛形の既定値は、すべてここから読みます。文書には「土台は `baseline.yaml` を見よ」とだけ書きます。

**最優先(2)**: **土台や方針を替えるときの手順を skill 1 本(例: `baseline-switch`)にする。** ユーザの痛みは「新しい方針を決めても古い資料が更新されない」という更新の場面なので、その場面の手順を固定します。

1. `baseline.yaml` を 1 行直す。
2. `docs/decisions/` に新しい記録を 1 本足す(古い記録は `status: superseded` にするだけで、本文は書き換えない)。
3. 自前の lint(`docs_index.py --check` を広げたもの)で、土台の ID を直書きしている「現行」の文書を列挙し、直すか `baseline.yaml` への参照に替える。
4. 冷読テストの固定の質問(下の (5))を回す。
5. 差分をユーザに 1 行で報告する。

あわせて、悪2 の「検索しやすい環境」への答えとして、CLAUDE.md に「問い → 正典 1 か所」の対応表(20 行程度)を置きます。実例です。

| 問い | 正典 |
|---|---|
| 今の土台と最良提出の構成は? | `data/derived/baseline.yaml` |
| ラベルを変えた実験はどの物差しで読む? | `.claude/rules/rulers.md` |
| 次にやることは? | `docs/research_program.md` の方向表と `docs/ideas.md` の未着手の行 |
| この方針はいつ誰が決めた? | `docs/decisions/INDEX.md`(効力のある記録だけ) |
| ある実験の数字は? | `outputs/exp/<exp>/results.json` → `data/derived/experiments.csv` |

**次に:**

- (3) **方針の変更を決定記録(ADR)で残す。** `docs/decisions/NNNN-<主題>.md` に `status: in-force|superseded`、`supersedes: [0009]`、`date:` を持たせます。一度 commit した記録は書き換えず、変えるときは新しい記録で置き換えます。`docs/decisions/INDEX.md` はスクリプトで生成し、効力のある記録だけを載せます。「新しい方針を決めても古い資料に古い方針が残る」への最も直接の処方です(Codeminer42 の記事、6 章)。
- (4) **lint を pre-commit か Stop hook に常設する。** 検査項目: 状態の行が無い / 状態が「現行」なのに本文に土台の ID を直書きしている / 2,000 字を超える行がある / 存在しないパスへのリンクがある / `docs/studies/` の新しいファイルが ideas・experiments・decisions のどこからも参照されていない。違反したら、直し方つきのメッセージを返します。
- (5) **冷読テストを定例にする。** 10-16 の「新しいセッション役に読み順の文書だけで 6 問に答えさせた」検査は良い型でした(commit 913e2233)。`tests/context_qa.yaml` に固定の質問と期待する答え(「今の土台は?」「提出の構成は?」「ラベルを変えた実験はどの物差しで読む?」など)を置き、土台を替えるたびと週 1 回、サブエージェントに答えさせて差分を出します。期待する答えは `baseline.yaml` から生成できます。

**余裕があれば:**

- (6) **`verified_at` と `depends_on` を、範囲を限って持たせる。** 247 本すべてではなく、INDEX で状態が「現行」の文書(今は約 15〜18 本)だけに付けます。例: `depends_on: [baseline, submission]`。`baseline.yaml` の `since` より古い `verified_at` の文書を、status.py が「要確認 N 件」として出します。
- (7) **追記型と上書き型を分ける。** `discussion.md` は「事実の節」を上書き型にし、更新の経過は `discussion_log.jsonl` に追記します。log.md は「1 行 = 1 事象、200 字以内」を lint で検査します。
- (8) **妨害文を検索から外す。** `archive/` と状態が「歴史的」の文書を既定の検索対象から外します(Grep は ripgrep を使うので `.ignore` が効く可能性がある。要確認)。または `permissions.deny` で `Read(archive/**)` を止め、必要なときだけ人が許可します。
- (9) **読み込み量に予算を設ける。** セッション開始時の読み物を合計 2 万トークン以内などと決め、status.py が超過を警告します。INDEX を全部読ませる代わりに、上の対応表を入口にします。

## 5. 振り返りに無かった論点

### 影響の大きい 3 件

1. **ユーザへの通知経路が無かった。** 完走・失敗・判断待ちを知らせる仕組みが hook にもスクリプトにも無く、判断待ちは ideas.md の「ユーザ判断待ち」に積まれるだけでした(log に「判断待ち」が 15 回)。サブ機からの取り込みも 11 回すべて、ユーザが「取り込んで」と言うまで待っていました。
   - 処方: ntfy などへの 1 行の通知を lane.py の完了時と Stop hook から呼ぶ(良3)。返事が無いときの既定の行動を night-run に書く。
2. **黙った失敗が繰り返された。** レビュー hook(2 日間全滅、Mac で 320 回以上)と、日次ウォッチの push 失敗(10-11〜13、10-19〜21。どちらも 2〜3 日気づかず)です。失敗の原因が push そのものだったため、「失敗を git に残す」設計でも失敗の行が届きませんでした。2 つの箱で日次ウォッチが同時に動いて衝突した時期もあり、cron の所在を一元管理していませんでした。
   - 処方: git 以外の通知経路と、STATUS.md に仕組みごとの「最終成功時刻」の欄。24 時間を超えたら警告を出す。
3. **「選別は 2 fold」の鉄則と実態がずれていた。** `results/*.yaml` の `folds` 欄で数えると、208 件のうち 5 fold が 139 件、2 fold が 35 件でした。320px の主モデルは 2 fold で約 3.2 時間、5 fold で約 8 時間かかり(CLAUDE.md の「2 fold で約 100 分」は 224px の頃の数字)、自律で回せる実験の数がおよそ半分以下になっていました。ユーザ指示によるものが多いので、方針として選ぶなら鉄則の方を書き換えるべきでした。
   - 処方: research_program.md に「この期間の fold 数の既定」を書き、5 fold は方向ごとの予算から引く。

### その他(1 行ずつ)

- 計画の権限とハーネスの権限の食い違い、期限と締切 → 3 章の良3。
- lane の外の GPU 利用(vLLM でのラベル作り)が記録に残らず、両 lane が 3 時間以上空いた計約 112 時間のうち本当に遊んでいた時間を測れない。lane に「外部の仕事」の種類を作るべきでした。

- 生成物を git で追跡した副作用: 日次ウォッチの別 clone で hook が INDEX.md を書き換えて rebase が止まり、翌日の `reset --hard` で 3 日分の push が消えた。生成物は追跡しないか、生成する場所を 1 か所に限るべきでした。

### 良かった点(振り返りに無かったもの)

- **事前登録と、物差しと LB の符号一致の台帳化。** 「dread(独立の物差しの 1 つ)の符号は LB と 9/11 一致、外れた 2 件は画像側へ寄せた施策」のように、手元の指標の限界を数字で持っていました。これがあったから「レポート由来の物差しは画像の読み手の比重を上げる施策を低く読む」という食い違いの型を見つけられました。研究エージェントの論文が警告する「自己評価が独立の検証に置き換わる」崩れ方への手当てとして、先進的です。
- **日次ウォッチの権限設計。** 隔離した clone、commit してよいファイルの許可リスト、Bash を与えない最小権限、失敗を git に残す作りです。自律運転の本体もこの水準にそろえられたはずです。

## 8. 見落としているかもしれないこと

- **会話の記録が無い。** vast.ai 上の transcript が無いので、「古い記述を読んで誤った」「会話の中で KB を使った」「ユーザが口頭で軌道修正した」回数は、文書と commit からの推定です。本文の古い記述の例は「置かれていた」証拠で、「参照されて誤った」証拠ではありません。
- **数え方で数字が揺れる。** Codex 由来の修正(204 件と 274 件)、禁止語の 24 回、土台の交代の回数などは件名や文言の grep によるもので、本文にだけ書かれた例や件名に書かれなかった修正は漏れています。人手と自動の判定の食い違いも、文字列で比べると 164 件、判定の種類で比べると 88 件と、比べ方で大きく変わります。途中停止の 37 件は、止めた主体の欄が無いので、ユーザ発とエージェント発を分けられていません。
- **起点の分類は note の文言に依存している。** 「ユーザ指示」と書かれていても、エージェントが提案してユーザが承認しただけのものが含まれている可能性があります。その場合、10 月の「エージェント発 8 件」は過小評価です。
- **稼働率は GPU の稼働の下限にすぎない。** lane の外の vLLM の仕事とサブ機 2 台は数に入っていません。
- **小手先の偏りの原因の比重は分からない。** 「研究方針の不在」「評価の構造(雑音 80%、終盤の物差しの解像度の喪失)」「ユーザ指示の偏り」「チーム内の分業(自分は単体を磨き、合成はチームで行う)」のどれが最も効いたかは切り分けていません。終盤は手元で読める改善が実際に残っていなかった可能性もあり、その局面ではアンサンブルが合理的な選択だったかもしれません。
- **提案した仕組みの多くは、このリポジトリでは未測。** hook での強制や必須欄は、形だけの記入(`--kb-refs "none: 不要"` の量産)を招くおそれがあります。導入したら評価課題と使用頻度の集計で効果を測り、効かない規則は外すべきです(Anthropic の「ハーネスの仮定は古くなる」)。
- **Web の知見の多くは別の課題での結果。** 研究エージェントの論文は MLE-bench などで、ソフトウェア開発の記事はコードベースの話です。医用画像の弱教師という今回の課題にそのまま当てはまるとは限りません。製品機能の記載は調査時点のもので、本稿の筆者が手元の版で動作を確かめたわけではありません。
- **CLAUDE.md の前提が「間違っていた」とまでは言えない。** ラベル以外の改善が大きかったのは、ラベル側の改善が手元の物差しで読みにくかったことの裏返しかもしれません。前提の見直しを定例にする提言は、どちらの読みでも成り立ちます。
- **この文書自体が将来の妨害文になりうる。** hook や権限設定の例を多く含むので、冒頭の状態の行のとおり「未適用の提言」として読んでください。採用したものは、正典(CLAUDE.md・`.claude/`・決定記録)の側に移し、この文書はその時点で「歴史的」に格下げするのがよいと考えます。
